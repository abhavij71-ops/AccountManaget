# نقشه راه فازهای بعدی — از ابزار شخصی به SaaS کوچک

🇬🇧 [Read in English](ROADMAP-SAAS.md)

این سند مسیر تبدیل Account Manager از یک ابزار تک‌کاربره به یک سرویس تیمی/SaaS را فاز به فاز توضیح می‌دهد، به‌همراه تصمیم‌های معماری و مواردی که عمداً نباید ساخته شوند.

---

## نکته حیاتی پیش از شروع

سند اصلی محصول (بخش ۵۲) صراحتاً Multi-user را از محدوده نسخه اول خارج کرده بود. این تصمیم درستی بود و برنامه به همین دلیل تمیز و سریع درآمد. اما تبدیل آن به SaaS **یک تغییر معماری بنیادی است، نه افزودن یک ماژول**.

دو پیامد که باید از ابتدا پذیرفته شوند:

**۱. مسئولیت امنیتی چند برابر می‌شود.** این برنامه رمز عبور ذخیره نمی‌کند، اما چیزی ذخیره می‌کند که برای مهاجم گاهی ارزشمندتر است: نقشه کاملِ «چه کسی، با چه ایمیلی، در چه سرویس‌هایی، با چه وضعیت 2FA و چه روش بازیابی». این یک سند شناسایی (reconnaissance) تمام‌عیار است. وقتی این نقشه برای ده‌ها سازمان روی یک سرور باشد، شما یک هدف با ارزش بالا شده‌اید.

**۲. هاست اشتراکی دیگر کافی نیست.** برای نسخه self-hosted تک‌تیمی بله، اما SaaS واقعی به cron قابل‌اتکا، ارسال ایمیل، backup خودکار و کنترل نسخه PHP نیاز دارد. از فاز ۱۵ به بعد VPS لازم می‌شود.

---

## فاز ۱۰ — لایه مالکیت (پیش‌نیاز همه‌چیز)

هیچ‌کدام از فازهای بعدی بدون این ممکن نیست. هم‌اکنون هیچ رکوردی «صاحب» ندارد.

### تصمیم معماری: یک دیتابیس به‌ازای هر Workspace

دو گزینه وجود دارد:

| رویکرد | مزیت | عیب |
|---|---|---|
| **Shared schema** — ستون `workspace_id` روی هر جدول | یک فایل، گزارش‌گیری آسان | یک `WHERE` فراموش‌شده = نشت اطلاعات بین مشتری‌ها |
| **یک فایل SQLite به‌ازای هر Workspace** ✅ | جداسازی فیزیکی، Export = کپی یک فایل، حذف = حذف یک فایل، قفل نوشتن تفکیک‌شده | مهاجرت schema باید روی همه فایل‌ها حلقه بزند |

**برای SQLite گزینه دوم به‌وضوح بهتر است.** ضعف اصلی SQLite (قفل تک‌نویسنده) با این کار به‌جای تشدید شدن، حل می‌شود: هر تیم قفل خودش را دارد و شلوغی یک مشتری روی بقیه اثر نمی‌گذارد.

```
data/
├── platform.sqlite            ← کاربران، workspaceها، عضویت‌ها، اشتراک‌ها
└── workspaces/
    ├── ws_000001.sqlite       ← داده تیم اول (همان ۱۶ جدول فعلی)
    ├── ws_000002.sqlite
    └── ...
```

### دیتابیس مرکزی

```sql
CREATE TABLE accounts_users (          -- کاربران پلتفرم
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    email TEXT NOT NULL UNIQUE COLLATE NOCASE,
    password_hash TEXT NOT NULL,
    full_name TEXT,
    preferred_language TEXT DEFAULT 'fa',
    timezone TEXT DEFAULT 'Asia/Tehran',
    is_active INTEGER NOT NULL DEFAULT 1,
    email_verified_at TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE workspaces (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    slug TEXT NOT NULL UNIQUE,
    db_file TEXT NOT NULL UNIQUE,      -- ws_000001.sqlite
    owner_user_id INTEGER NOT NULL REFERENCES accounts_users(id),
    plan TEXT NOT NULL DEFAULT 'free',
    status TEXT NOT NULL DEFAULT 'active',
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE memberships (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    workspace_id INTEGER NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id INTEGER NOT NULL REFERENCES accounts_users(id) ON DELETE CASCADE,
    role TEXT NOT NULL CHECK (role IN ('owner','admin','member','viewer')),
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE (workspace_id, user_id)
);
```

### تغییرات لازم در کد

۱. `db.php` باید بر اساس `$_SESSION['workspace_id']` فایل درست را باز کند.
۲. یک **Migration Runner** بسازید: اسکریپتی که نسخه schema هر فایل را می‌خواند و مهاجرت‌های عقب‌افتاده را اعمال می‌کند. بدون این، از فردا هر تغییر schema غیرممکن می‌شود.
۳. جدول `schema_version` داخل هر فایل workspace.
۴. مهاجرت کاربر فعلی: دیتابیس موجود به `ws_000001.sqlite` تغییر نام یابد و یک workspace برایش ساخته شود.

## فاز ۱۱ — تیم و نقش‌ها

### چهار نقش، نه بیشتر

| نقش | مجوزها |
|---|---|
| **Owner** | همه‌چیز + حذف workspace + مدیریت اشتراک |
| **Admin** | همه داده‌ها + دعوت/حذف عضو |
| **Member** | ساخت و ویرایش داده خودش؛ مشاهده داده مشترک |
| **Viewer** | فقط مشاهده، بدون ویرایش |

از ساخت سیستم مجوز جزئی (per-entity permission) خودداری کنید — سند اصلی در بخش ۵۲ صراحتاً آن را رد کرده و در عمل هیچ تیم کوچکی از آن استفاده نمی‌کند.

### مالکیت رکورد درون Workspace

```sql
-- روی هر چهار جدول اصلی
ALTER TABLE emails   ADD COLUMN owner_user_id INTEGER;
ALTER TABLE accounts ADD COLUMN owner_user_id INTEGER;
ALTER TABLE services ADD COLUMN owner_user_id INTEGER;
ALTER TABLE phones   ADD COLUMN owner_user_id INTEGER;

-- سطح دیده‌شدن
ALTER TABLE emails   ADD COLUMN visibility TEXT NOT NULL DEFAULT 'workspace'
    CHECK (visibility IN ('private','workspace'));
```

**قانون:** `private` یعنی فقط صاحب رکورد و Ownerِ workspace می‌بینند. `workspace` یعنی همه اعضا می‌بینند.

### دعوت اعضا

```sql
CREATE TABLE invitations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    workspace_id INTEGER NOT NULL,
    email TEXT NOT NULL,
    role TEXT NOT NULL,
    token TEXT NOT NULL UNIQUE,
    expires_at TEXT NOT NULL,
    accepted_at TEXT,
    invited_by INTEGER NOT NULL
);
```

توکن باید با `bin2hex(random_bytes(32))` ساخته شود و انقضای ۷ روزه داشته باشد.

## فاز ۱۲ — حریم خصوصی درون‌تیمی

این فاز چیزی است که معمولاً فراموش می‌شود و بعداً باعث بی‌اعتمادی می‌شود.

۱. **کارمند باید بتواند اکانت شخصی‌اش را `private` بگذارد.** اگر همه‌چیز برای Admin قابل مشاهده باشد، کارمند اطلاعات واقعی وارد نمی‌کند و داده بی‌ارزش می‌شود.
۲. **Admin باید بداند چه چیزی را نمی‌بیند.** نمایش «۳ رکورد خصوصی» بدون افشای محتوا — شفافیت بدون نقض حریم خصوصی.
۳. **هنگام خروج عضو از تیم**، سه گزینه صریح: انتقال مالکیت به فرد دیگر / آرشیو / حذف. هرگز حذف خودکار نشود.

---

## فاز ۱۳ — سخت‌سازی امنیتی سطح SaaS

پیش از پذیرش اولین مشتری واقعی، این موارد الزامی هستند:

1. **محدودسازی نرخ ورود** — قفل موقت پس از ۵ تلاش ناموفق، بر اساس IP و نام کاربری
2. **2FA برای خود برنامه** — TOTP با `RobThree/TwoFactorAuth` یا پیاده‌سازی مستقیم (الگوریتم ساده است). بدون این، فروش به هیچ سازمانی ممکن نیست
3. **مدیریت نشست** — فهرست دستگاه‌های فعال + دکمه «خروج از همه دستگاه‌ها»
4. **Audit Log جدا از History** — `history` تغییرات داده را ثبت می‌کند؛ audit log باید **دسترسی** را ثبت کند: چه کسی، چه زمانی، چه رکوردی را دید
5. **Backup خودکار** — cron روزانه که هر فایل workspace را با فشرده‌سازی و timestamp کپی کند
6. **هدرهای امنیتی** — `Content-Security-Policy`, `X-Frame-Options: DENY`, `Strict-Transport-Security`
7. **رمزگذاری فایل در حالت سکون** — اگر VPS اشتراکی است، دست‌کم SQLCipher را بررسی کنید

## فاز ۱۴ — تمایز محصول (مهم‌ترین فاز تجاری)

تا اینجا یک ابزار سازمان‌یافته ساخته‌اید. اما هیچ‌کس برای «صفحه‌کلید منظم‌تر از اکسل» پول نمی‌دهد. این سه قابلیت چیزی هستند که محصول را فروختنی می‌کنند:

### ۱. گردش کار خروج کارمند (Offboarding) — قوی‌ترین گزینه

سؤالی که هر مدیر IT هفته‌ای یک‌بار با آن روبه‌روست: **«علی از شرکت رفت — به چه چیزهایی دسترسی داشت؟»**

یک صفحه که با انتخاب یک عضو، چک‌لیست کامل تولید کند: تمام اکانت‌هایی که مالک بوده، تمام سرویس‌هایی که ایمیل کاری او در آن‌ها ثبت شده، تمام اشتراک‌های پولی به‌نام او، تمام شماره‌هایی که به‌عنوان Recovery ثبت شده. با امکان تیک زدن «انجام شد» و خروجی PDF برای بایگانی.

**این یک درد واقعی و قابل‌فروش است.** برای شرکت‌های ۱۰ تا ۱۰۰ نفره در ایران و عراق که هیچ ابزار بین‌المللی (Torii, Zluri, BetterCloud) به آن‌ها سرویس نمی‌دهد، این یک بازار خالی است.

### ۲. بازبینی دوره‌ای دسترسی (Access Review)

یک کمپین سه‌ماهه: سیستم برای هر عضو فهرست اکانت‌هایش را می‌فرستد و از او می‌خواهد تأیید کند که هنوز لازم است. نتیجه: داده همیشه تازه می‌ماند و مدیر گزارش انطباق می‌گیرد.

### ۳. کشف اشتراک‌های فراموش‌شده (Shadow SaaS)

گزارش: «۴ اشتراک پولی دارید که در ۹۰ روز گذشته هیچ ورودی نداشته‌اند — مجموع ۱۲۰ دلار در ماه.» این قابلیت خودش هزینه اشتراک شما را توجیه می‌کند و بهترین استدلال فروش است.

## فاز ۱۵ — اعلان و اتوماسیون

۱. **ایمیل** — دعوت عضو، بازنشانی رمز، هشدار تمدید اشتراک. با SMTP (نه `mail()`) و صف ساده مبتنی بر جدول
۲. **پیامک/واتساپ** — برای بازار ایران و عراق کاربردی‌تر از ایمیل است
۳. **Cron واحد** — یک فایل `cron.php` که هر شب اجرا می‌شود: بررسی تمدیدها، بازمحاسبه امتیاز امنیتی، backup، پاکسازی توکن‌های منقضی
۴. **Webhook خروجی** — اتصال به Slack یا Bale برای هشدارهای Critical

---

## فاز ۱۶ — مکانیک SaaS

۱. **ثبت‌نام خودسرویس** با تأیید ایمیل و ساخت خودکار workspace
۲. **پلن‌بندی با محدودیت قابل‌اعمال** — مثلاً: رایگان تا ۳ عضو و ۵۰ اکانت / حرفه‌ای بدون محدودیت. محدودیت باید در سطح کد اعمال شود، نه فقط در صفحه قیمت
۳. **پرداخت** — برای بازار ایران: زرین‌پال یا درگاه مستقیم بانکی. برای بازار عراق: پرداخت دستی + فعال‌سازی توسط ادمین کاملاً قابل قبول است
۴. **پنل ادمین پلتفرم** — فهرست workspaceها، وضعیت اشتراک، حجم فایل، امکان تعلیق
5. **Export کامل و حذف حساب** — کاربر باید بتواند فایل SQLite خودش را دانلود کند و حساب را حذف کند. این برای اعتمادسازی حیاتی است

---

## چه چیزهایی را نسازید

۱. **سیستم مجوز جزئی (per-field / per-record permission)** — پیچیدگی‌اش نمایی است و هیچ تیم کوچکی استفاده نمی‌کند
۲. **ذخیره رمز عبور** — لحظه‌ای که این کار را بکنید، محصولتان یک Password Manager ضعیف می‌شود که با Bitwarden و 1Password رقابت می‌کند و می‌بازد. اصل نهایی سند را حفظ کنید
۳. **کشف خودکار اکانت‌ها از طریق OAuth** — نیازمند بررسی امنیتی هر سرویس، نگهداری توکن و مسئولیت حقوقی. برای این مقیاس ارزشش را ندارد
۴. **اپلیکیشن موبایل بومی** — یک PWA با همین کد ۹۰٪ همان ارزش را با ۵٪ هزینه می‌دهد
۵. **بازنویسی با فریم‌ورک** — تا وقتی PHP خالص کار می‌کند، Laravel فقط پیچیدگی و هزینه هاست اضافه می‌کند

## ترتیب پیشنهادی و تخمین

| فاز | موضوع | حجم نسبی | ضروری برای SaaS؟ |
|---|---|---|---|
| ۱۰ | لایه مالکیت + Migration Runner | بزرگ | بله — پیش‌نیاز مطلق |
| ۱۱ | تیم و نقش‌ها | بزرگ | بله |
| ۱۲ | حریم خصوصی درون‌تیمی | متوسط | بله |
| ۱۳ | سخت‌سازی امنیتی | متوسط | بله — پیش از اولین مشتری |
| ۱۴ | تمایز محصول (Offboarding) | متوسط | بله — بدون آن فروش ندارید |
| ۱۵ | اعلان و اتوماسیون | متوسط | تا حدی |
| ۱۶ | مکانیک SaaS و پرداخت | بزرگ | فقط برای نسخه میزبانی‌شده |

**پیشنهاد مسیر کم‌ریسک:** فازهای ۱۰ تا ۱۴ را بسازید و ابتدا به‌عنوان **نسخه self-hosted با لایسنس** بفروشید. مشتری روی هاست خودش نصب می‌کند، شما مسئولیت امنیتی نگهداری داده دیگران را ندارید، و بازخورد واقعی می‌گیرید. اگر تقاضا ثابت شد، فاز ۱۶ و میزبانی را اضافه کنید.
