# سیاست شاخه‌بندی (Branching)

Account Manager به‌صورت **دو نسخهٔ دائمی روی دو شاخه (Branch)** نگهداری می‌شود، نه یک کدبیس واحد پشت یک Flag که در زمان اجرا تصمیم می‌گیرد. کارهای Part B (توسعهٔ چندکاربره/SaaS) مسیر `db()`، تمام کوئری‌های فهرست و جستجو، و جدول‌های احراز هویت را تغییر می‌دهد — عبور دادن دو مسیر منطقی از میان همهٔ این‌ها، در پروژه‌ای بدون مجموعه تست خودکار، سطح شکست را برای یک تمایز که ساختاری است (نه چیزی که باید در زمان درخواست با یک تنظیم تصمیم‌گیری شود) دوبرابر می‌کند.

## دو نسخه

| | `single-user` | `main` |
|---|---|---|
| مخاطب | یک نفر، یک نصب، بدون تیم | تیم‌ها، چند Workspace، SaaS میزبانی‌شده یا Self-hosted |
| نسخه‌گذاری | `v1.x.x` | `v2.x.x` |
| وضعیت | فریزشده از نظر امکانات — فقط رفع باگ و رفع مشکلات امنیتی | توسعهٔ فعال |
| مدل داده | یک فایل SQLite | دیتابیس مرکزی Platform + یک فایل SQLite برای هر Workspace |
| معرفی به‌عنوان | یک نسخهٔ دائمی و پشتیبانی‌شده | «آخرین» نسخهٔ منتشرشده |

## قوانین

1. **`single-user` هرگز امکان جدید دریافت نمی‌کند.** این شاخه در آخرین Commit پیش از شروع کار چندکاربره/SaaS فریز شده است. فقط رفع باگ و رفع مشکلات امنیتی، برای همیشه، روی آن اعمال می‌شود — این شاخه رهاشده نیست، بلکه یک محصول دائماً نگهداری‌شده برای کسانی است که هرگز به چند Workspace نیاز نخواهند داشت.
2. **رفع مشکلات ابتدا روی `single-user` انجام می‌شود، سپس به‌جلو (Forward) در `main` Merge می‌شود.** `main` از نقطهٔ انشعاب `single-user` منشعب شده، پس `single-user` → `main` یک Merge ساده و مکانیکی در طول یک خط تبارشناسی واقعی است. جهت برعکس (`main` → `single-user`) اصلاً یک Merge نیست — `main` دارای Workspace، Membership و یک دیتابیس مرکزی Platform است که `single-user` آن‌ها را ندارد، پس رفع مشکلی که برای `main` نوشته شده را نمی‌توان بدون بازنویسی دستی بر اساس Schema دیگری، روی `single-user` اعمال کرد. با اعمال ابتدایی روی شاخهٔ قدیمی‌تر و سپس Merge به‌جلو، از این بازنویسی برای هر رفع مشکل جلوگیری می‌شود.
3. **شماره نسخه به‌روشنی نشان می‌دهد کدام نسخه است.** `v1.x.x` همیشه یعنی `single-user`. `v2.x.x` همیشه یعنی نسخهٔ SaaS روی `main`. هیچ‌کس لازم نیست نام Branch را چک کند تا بفهمد یک شماره نسخه مربوط به کدام نسخه است.
4. **`main` همیشه به‌عنوان نسخهٔ فعلی معرفی می‌شود.** هرکس بپرسد «آخرین نسخهٔ Account Manager چیست»، آخرین Tag با فرمت `v2.x.x` روی `main` را دریافت می‌کند. `single-user` به‌عنوان یک گزینهٔ جایگزین و آگاهانه برای کسانی که آن را می‌خواهند ارائه می‌شود — نه پنهان، نه پیش‌فرض.

## اعمال یک رفع مشکل

```bash
git checkout single-user
# ... رفع مشکل را انجام دهید و Commit کنید ...
git tag v1.x.y
git checkout main
git merge single-user   # Merge به‌جلو — مکانیکی، نه بازنویسی
# در صورت وجود، تعارض‌ها را حل کنید (باید نادر باشند و فقط در کدی که دو نسخه هنوز مشترک هستند)
git push origin single-user main v1.x.y
```

اگر فایل موردنظر دیگر روی هر دو شاخه به همان شکل وجود نداشته باشد (مثلاً منطق مسیریابی Workspace در `db.php`)، این یک رفع مشترک نیست — آن را به‌صورت جداگانه روی هر شاخه بنویسید و Commit کنید، نه با Merge.

## انتشار نسخه

برای ساخت فایل zip قابل توزیع یک Tag مشخص، از `tools/build-release.sh <ref> <single-user|saas>` استفاده کنید. توضیحات داخل همان اسکریپت، و `.github/workflows/release.yml` برای نسخهٔ خودکار (اختیاری) را ببینید.
